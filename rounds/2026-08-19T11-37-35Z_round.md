## explorer (explorer-5)

`tools/direction.py` shows three families sitting at literally zero runs and buildable by `tools/make_variant.py`: capacity (depth/dim/mlp), objective (mtp/zloss), and signal_path (noqknorm) — `mtp` and `zloss` and `noqknorm` all read "NEVER TRIED" in the mechanism table. `signal_scale` (rope/softcap/x0init) is correctly excluded per the brief: none of those emits a metric a diagnostic can bind to. `input_pipeline`'s only registered mechanism, `prefetch`, has no branch in `make_variant.build()` — `_IMPLEMENTED` only contains `{mtp, unet, zloss, noqknorm, precond}` — so building it raises `VariantEditError`; it needs new code, not a config, and I am not proposing it as a runnable variant this round. `attention_detail` already has `n=4` (qk_suppress, open) so it is lower priority than a true zero.

I verified all four proposals build cleanly against baseline and checked each diagnostic against the real control corpus with `claims.diagnostic_would_discriminate`.

**1. capacity / mlp=2** — `{"dbs":128,"tbs":19,"mlp":2,"dim":512,"depth":8}`. Halving the MLP hidden ratio cuts `flops_per_token_M` well below the baseline's fixed 239.078, buying step count under L019's cost model — the mirror image of the confirmed `ve=1` win (params added at zero FLOP cost). This asks whether the model is over-provisioned in MLP capacity relative to the ~1000-step budget. Diagnostic: `flops_per_token_M lt 230` — verified, 76/76 controls fail (all sit at the fixed baseline value), true separation.

**2. capacity / dim=640** — `{"dbs":128,"tbs":19,"mlp":4,"dim":512→640,"depth":8}` (5 heads at HEAD_DIM=128). The expensive-direction twin of #1: raises capacity and cost together. Pairing these two is the highest-information single probe of a totally unmeasured axis because it reads the SIGN of the capacity/step-count trade, not just one point on it. Diagnostic: `n_embd eq 640` — verified, 78/78 controls fail (all report 512).

**3. objective / mtp=0.3** — `{"dbs":128,"tbs":19,"mlp":4,"dim":512,"depth":8,"mtp":0.3}`. Adds a DeepSeek-V3-style auxiliary t+2 prediction head sharing the main `lm_head`, weighted 0.3, gated off at eval so `val_bpb` accounting is untouched. `mtp_proj` is zero-initialized, so any nonzero final RMS is proof the optimizer actually used the new path rather than the aux loss degenerating into label smoothing (the L014-class failure the code comments call out explicitly). Diagnostic: `mtp_proj_rms gt 0.0`. This field is mechanism-only (no control ever emits it), so `diagnostic_would_discriminate` returns "no control has emitted yet; cannot pre-check" rather than a real cross-arm separation — flagging that limitation rather than hiding it. `zloss=0.0001` is a lower-priority backup in the same family with the same caveat.

**4. signal_path / noqknorm=1** — `{"dbs":128,"tbs":19,"mlp":4,"dim":512,"depth":8,"noqknorm":1}`. Drops the RMS-norm on q/k before attention. Unlike mtp/zloss, this diagnostic has real cross-arm teeth: `qk_q_rms_final`/`qk_k_rms_final` are emitted unconditionally by every variant — control prints the post-norm RMS (pinned near 1 by construction), treatment prints the raw pre-norm RMS. Verified both `lt 0.7` and `gt 1.3` separate cleanly (45/45 controls fail each), so either drift direction is falsifiable against the real corpus, not just a trivial "no control yet" pass.

All four hold `tbs=19` (baseline) rather than stacking on the confirmed `tbs=18` lever, to keep the new axis's read clean and unconfounded; stacking is a follow-up once a direction shows signal, per `plateau-switch-to-mechanisms` discipline. Recommend running #1/#2 as a same-wave counterbalanced pair (they are natural opposites) and #4 as the strongest single mechanism bet given its diagnostic actually discriminates against real data today.

## critic (critic-5)

Lessons checked: L045 (step-indexed momentum confound), L020 (GPU not core block), L007 (ns no-op), L030 (activation predicate the control also passes), plus the dry-rule/exploitation/E3 policy comments embedded in direction.py, coe.py and balance.py that document the six rule changes named in the brief. I also read baseline/train.py directly rather than trusting any summary of it.

**1. The tbs=18 confound is worse than L045 states, and the queued arm does not close it.** `grad_accum_steps = TOTAL_BATCH_SIZE // tokens_per_fwdbwd` (train.py:504) is the only quantity `tbs` moves, and it fans out into at least THREE step-indexed mechanisms, not one:
- `get_muon_momentum(step)` (train.py:534) — the one L045 names, addressed by the queued `mu_warmup=600` arm (R5MU_A/B).
- Adam bias correction, `bias1 = 1 - beta1_t**step_t`, `bias2 = 1 - beta2_t**step_t` (train.py:317-318, called from `_step_adamw`, state['step'] incremented once per outer step). This governs lm_head, embedding, value-embedding, resid-scalar and x0-scalar params (train.py:258-262) — a real slice of the model, not a corner case. Doubling steps-per-300s does not change the *fraction* this occupies the way the momentum ramp does (it decays in ~5-20 absolute steps regardless), but it means the Adam-managed groups get roughly 2x as many gradient updates within the fixed wall-clock budget, independent of anything Muon does. `mu_warmup` never touches this. No queued arm isolates it.
- The raw update-count effect itself: even with `mu_warmup=600` holding the momentum ramp at a fixed fraction, tbs=18 still delivers ~2x total optimizer steps in 300s versus tbs=19. That is arguably the actual critical-batch-size hypothesis under test, so it's not improper to leave it moving — but it means R5MU is a **partial** deconfound, not a full one: it isolates the ramp-fraction effect from "more updates," but it does not isolate Adam's bias-correction dynamics from either. I did not find a third arm queued for that. I checked `(step+1) % 5000 == 0` (gc.collect trigger) and `debiased_smooth_loss`'s `ema_beta**(step+1)` — both confirmed inert at these step counts (max step count observed is 2003, so gc.collect never fires) or purely a print-only diagnostic that never touches the optimizer state, so neither is a real confound. Verdict: the two queued arms (R5MU mu_warmup, R5MC mu_ceil) are necessary but the campaign should register a lesson naming the Adam bias-correction schedule as a second, smaller, still-unaddressed step-indexed confound before calling tbs=18 "explained."

**2. mu_ceil=0.9823 is false precision, not unsound in principle.** The derivation (`alpha_1 = alpha_0*(b1/b0)*sqrt(T0/T1)`, make_variant.py:349-354) reproduces correctly: alpha_0=0.05, b1/b0=0.5, solving backward from the stated 0.01768 requires T0/T1=0.5, i.e. the rule is being invoked with T = step count at fixed token budget, doubling because tbs=18 halves tokens/step. That's an internally consistent read of a plausible published co-scaling law. Two things are unverified: (a) the rule's source paper almost certainly derives it asymptotically for plain momentum/Adam-style optimizers at scale, not for Newton-Schulz-orthogonalized Muon at 50M params and ~2000 steps — applying it here is an extrapolation across BOTH scale and optimizer family; (b) a single point estimate (0.9823) treated as "the answer" is a stronger claim than "a candidate value worth testing," and the queued arm (R5MC, one value) cannot distinguish "the co-scaling rule is right" from "any higher ceiling helps at this batch size" from "no effect at this n." What would falsify the derivation itself: a 3+ rung ladder (e.g. 0.95 baseline, ~0.97, 0.9823, 0.99) at fixed tbs=18 — if val_bpb is monotone toward 0.9823 and turns back up past it, that's real support; if it's monotone past 0.9823 or flat, the rule doesn't transfer at this scale and the specific decimal was theater. As specified, R5MC tests only "is 0.9823 better than 0.95," which is a weaker and different claim than "the co-scaling rule is correct."

**3. The search is not literally incapable of closing — right now, nothing IS closed.** `analyze.py`'s axis table shows every touched axis (ns, qk_suppress, swdiv, tbs, ve, wd_const) at `dry` 1-2, all "open," zero at DRY_STREAK=4. Given the mechanics (dry counts DISTINCT values, not runs, so a 4-run counterbalanced quad of one value only ever advances the streak by 1; plus the best-holder exemption keeps an axis open indefinitely while `since_best < 4`), closing an axis now requires 4 distinct rungs that all fail to beat the *device-corrected* global best while the axis is not currently leading. That is a materially higher bar than before, and empirically it has produced zero closures against 6 explored axes and 17 still-virgin ones. Given 17/23 axes are UNEXPLORED and rank as top priority, this is not currently costing anything — the search hasn't reached the point where closure would matter. But the operator should recognize the ratchet: six consecutive individually-justified loosenings (each fixing a real, documented prior failure — closing `ve` after one win, DRY_STREAK counting quad-runs as 4 strikes, freezing the audit on a known-dead diagnostic, an unreachable 12.5%-ceiling exploit share, an unlaunchable mu_const target) have moved the policy from "closes too eagerly" to a regime that, as configured, has not closed a single axis across 125 runs. If that persists once the virgin axes are filled, the balance ledger and dry rule will have no teeth left to redirect budget away from axes that are genuinely flat — worth a explicit stress test (synthetic axis with 4 distinct clearly-losing values) to confirm closure still fires at all before trusting it under load.

**4. Seed 42, n=1, one device — the claims must stay narrow.** I confirmed directly: every valid result record's `metrics.seed` is 42.0 or absent (absent = invalid/non-activated run); grep of train.py shows `torch.manual_seed(SEED)` / `torch.cuda.manual_seed(SEED)` with `SEED = int(os.environ.get("AUTORESEARCH_SEED","42"))` — overridable but never overridden in any run on disk. The "counterbalanced quad" replicate structure (s0-s3) is GPU/device counterbalancing per L020, not seed diversity — confirmed by the per-GPU device model in analyze.py's DEVICE MODEL section, which is keyed on `gpu`, not seed. What MAY be claimed: 0.984017 is the true raw val_bpb of that exact byte-identical config, seed, and device population at 300±wall-clock-noise seconds, and it beats the measured control distribution by far more than the 0.00219 noise band (t=-60.7 stated for the underlying tbs effect). What may NOT be claimed: that this is the best achievable seed for this config (single-seed noise floor lesson elsewhere in the corpus already flags σ~0.0006 at 5-min frames as 72% of a gate — that's seed-to-seed variance this campaign has never measured here), that the ranking of configs is stable across seeds, or that anything about generalization beyond this exact data/tokenizer/step regime holds. A true SOTA claim for publication would need ≥3 seeds per config at minimum; right now every "best" is one draw.

Lessons the queued experiments risk violating.** R5MC (mu_ceil) and R5MU (mu_warmup) both stack on top of tbs=18, which is fine per the exploitation exemption (reusing tbs's own best-known value is allowed even were tbs closed) — but both are single-value arms on axes L045 itself says exist BECAUSE of an unresolved confound family; registering either as a clean "mu_ceil helps" or "mu_warmup deconfounds tbs" result without first checking Adam bias-correction (point 1) would repeat the exact overclaim pattern L045 was written to stop. **Minimum viable selector.** One file, `tools/selector.py`, reading only existing records — no new instrumentation. Candidates come from the same fixed knob grid `make_variant.py` already supports. For each candidate `c`:
- `novelty(c)` = 1.0 if its axis has n=0 runs (direction.py table), else `1/(1+n)`.
- `activatable(c)` = hard 0/1 gate: dry-run `make_variant.build(c)` succeeds AND `claims.diagnostic_would_discriminate(diag, rule)` returns True for its declared diagnostic. Fails → score 0, never proposed.
- `expected_gain(c)`: if the axis has ≥1 rung and `balance.py`'s ladder says CONTINUE, use 0.5×|last marginal delta| (shrunk-linear extrapolation); if virgin, use a weak prior = median |confirmed-lever effect| (≈0.0027 today) × 0.3; if the axis's best rung already lost, 0.
- `cost(c)` = GPU-minutes for one counterbalanced quad-pair (≈8 arms × 300s ≈ 40 GPU-min), scaled up by `flops_per_token_M(c)/239.078` as a throughput-risk multiplier.
- `blocked(c)` = 0 if any active lesson's `blocks_keys` intersects `c`'s keys, else 1.
- `score(c) = blocked(c) × activatable(c) × (novelty(c) + expected_gain(c)) / cost(c)`.
Batch selection: sort by score, greedily take the top candidate, then for each subsequent pick multiply remaining scores by 0.2 for any candidate sharing a *family* (direction.py's family column) with an already-picked candidate, repeat until k=3. This gets diversity without an optimizer — it's the same discipline the campaign already uses for per-device counterbalancing, applied to family coverage instead of GPU slot.
