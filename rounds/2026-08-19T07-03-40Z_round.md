## explorer (explorer-3)

Sixty-six runs have almost exclusively hit `optimizer_numeric` (precond, ns, wd_const): 5 of 20 knob axes and 1 of 6 mechanisms have any coverage at all. `capacity`, `objective`, `signal_path`, `token_exposure`, and `signal_scale` are all at n=0 and rank top-priority in `direction.py`. Four proposals, ordered by expected information:

**1. Capacity iso-shape swap (`depth`/`dim`, family `capacity`, 0 runs).** `head_dim=128` is fixed, so `dim` only takes multiples of 128; num_heads follows. Propose `{"depth": 10, "dim": 384}` (deeper/narrower, ~num_heads=3) against control `{"depth": 8, "dim": 512}` (num_heads=4). This is the one axis where a totally different capacity allocation has never been sampled once, despite depth being consistently the stronger lever for bpb at fixed-ish params in short-horizon LM literature. Mechanism: reallocating params from width (quadratic in attn/mlp cost) to depth (linear) changes per-token FLOPs and thus step count — falls under L019's "not free" warning, so the prediction is on **raw val_bpb**, not a step-controlled residual: depth-heavy allocation should show lower loss-per-token that either does or does not survive the throughput hit. Predicted |Δ| ≈ 0.001–0.003, clears resolution either direction. Falsifier: if step count drops enough that raw val_bpb is worse despite lower per-token loss, the FLOP cost dominates and the axis is closed for "buy depth" configs at this budget.

**2. `mtp` mechanism (objective, 0 runs, `_IMPLEMENTED`).** Auxiliary t+2 cross-entropy head off a zero-init projection, added at constant weight (code does NOT anneal despite the comment — verified by reading `make_variant.py`: `MTP_W = cfg['mtp']` is a fixed scalar). Propose `{"mtp": 0.1}`. Mechanism: denser per-token supervision should sharpen shared early-layer representations within 1000 steps, similar to DeepSeek-V3's MTP auxiliary loss. Near-zero added FLOPs (one extra linear + softcap + CE on the same hidden states). Predicted −0.0005 to −0.0015. Falsifier: `mtp_proj_rms` stays ~0 (non-activation, inconclusive) or moves but val_bpb is flat/worse (auxiliary loss competes with the primary objective for optimizer capacity — the specific failure mode this benchmark's short horizon would produce).

**3. `unet` mechanism (signal_path, 0 runs).** Zero-init learned cross-depth skip connections (`skip_lambdas`), so the arm starts bit-identical to control — any movement is proof of engagement, not placebo. Propose `{"unet": 1}`. Near-zero cost (one extra elementwise add per lower-half layer, no new matmul). Predicted −0.0005 to −0.002, drawing on modded-nanogpt speedrun lineage where U-net-style skips are a standing component. Falsifier: `skip_lambda_absmean` ≈ 0 at end of run (dead weight, inconclusive) vs. non-trivial magnitude with no bpb gain (real negative).

**4. `tbs` (token_exposure, 0 runs).** Propose `{"tbs": 20}` (2**20 = 1,048,576 tokens/step, double baseline) vs `{"tbs": 18}` (half). Mechanism: this run sits near the 2-epoch overfitting boundary (per campaign memory); larger batches give fewer, lower-variance updates over the same token budget, which literature ties to critical-batch-size effects — plausibly reducing the noisy-gradient contribution to val_bpb independent of FLOPs. Cost is CPU-proportional (repacking), not GPU-FLOP, so it's a genuinely different cost axis than capacity. Predicted |Δ| ≈ 0.0008–0.002. Falsifier: raw val_bpb move is dominated by the step-count shift alone (consistent with the measured −0.0669/e-fold law) with no residual beyond that law — i.e., it's just the throughput result already known, not a new batch-size effect.

All four are expressible directly via `tools/make_variant.py`'s existing `cfg` keys (`depth`, `dim`, `mtp`, `unet`, `tbs`) with no new code required, and all clear the 0.000271 GPU-counterbalanced resolution if the predicted magnitude is anywhere near right. I'd sequence capacity and mtp first — capacity because it is the single most under-sampled family in the whole ledger (three axes at n=0 simultaneously), mtp because it is cheapest to falsify cleanly (its activation observable, `mtp_proj_rms`, is unambiguous by construction).

## pragmatist (pragmatist-3)

Cheapest real gain available right now costs zero GPU time: **adopt `precond` into the base config.** It's been replicated n=7, best 0.990345, and every precond arm in `runs/sweep/results` sits below the control cluster by roughly -0.0011 to -0.0006, well clear of the 0.000271 GPU-counterbalanced resolution and the code comment confirms it's a pure reorder of an existing block (no new tensor, fused update stays intact) — so it doesn't cost steps either. There is nothing left to learn from re-running it. The only real cost is bookkeeping: once `baseline/train.py` bakes in the pre-orthogonalization NorMuon reorder, every future "control" shifts by ~-0.001, so the 43-run historical ALL-CONTROL SPREAD and the per-GPU DEVICE MODEL in `tools/analyze.py` stop being poolable with new runs — they need a footnote marking them pre-adoption, and the first post-adoption wave should include at least one fresh counterbalanced control pair so `direction.py`'s noise band isn't silently computed across the regime change. That's a one-wave tax, not a blocker. Do it now, don't spend another pair confirming it.

With that banked, the two GPUs are already committed to the queued `ve` 2→1 and `swdiv` 2→4 blocks (8 wave_groups, ~64 min) — don't touch those. For what comes after, rank by GPU cost, not novelty: `qk_suppress` (D4, critic-cleared, zero added FLOPs, buildable today) and `unet` (near-free skip-connection reorder, buildable today, zero mechanism runs so far) are the next-cheapest real mechanism tests and should go in the following slot. Behind those, single cheap probes of `warmup`, `mu_const`, `x0init` (all flagged "free" cost, all UNEXPLORED, all buildable) are worth a pair each opportunistically. Deprioritize `compile_mode` — CV 6.96% on step count means it needs many replicates to resolve, and it's explicitly "the most wave-confounded thing to measure," bad ROI on 2 GPUs. Deprioritize `mtp` (materializes a [B,T,V] tensor, real GPU/memory cost, uncertain payoff) and the `depth/dim/mlp` capacity axis (mfu ~42.6% means added FLOPs directly cost steps). Do not spend anything on `ns` or `wd_const` — both already have 2 dry replicates each and `wd_const`'s best (1.001430) is far worse than the current best, that axis reads as closed. Do not propose `prefetch` — it's listed as a mechanism but has no branch in `make_variant.py`; running it silently produces the control source, so it needs new code before it's a real experiment, not GPU time today.

## critic (critic-3)

Checked against: L003 (wave split silently), L004/L009 (dispatcher bookkeeping), L020 (device offset is GPU not core block), L028 (precond re-homed into optimizer_numeric), L029 (control budget outgrew its purpose), L030 (activation predicate the control also passes), L031 (stranded treatments), L032 (wd_const≥0.4 blocked), L033 (component share ≠ intervention share) — plus a live check of `tools/gpu_watch.py`, which right now shows only gpu6/gpu7 free (gpu0-3 held by guoshaoyang, gpu4/5 by yangleqian).

**1. The 2-wide pair design.** This is NOT the same failure the prompt implies. Each R2V/R2S pair (`R2V_P1..P4`, `R2S_P1..P4`) launches treat+control in one `wave_group`, so within a pair the shared-host-condition guarantee CLAUDE.md requires is intact — that part is sound and I will not manufacture a problem where none exists. The real risk is device-offset cancellation. Right now gpu6/gpu7 are the *only* free GPUs, so every pair's two members land on exactly those two devices, whose control means differ by 0.00049 (gpu6 0.991667 vs gpu7 0.991177) — 1.8x the predicted swdiv/ve effect (0.0006). Slot alternates across pairs (treat=s0,s1,s1,s0), which cancels this offset only in the 4-pair *average*, and only if slot maps to physical GPU deterministically and gpu4/5 stay foreign-held for the whole run. If a foreign tenant frees a GPU mid-campaign and a later pair lands on a third device, the 2-2 balance breaks and an individual pair's diff carries up to ~0.0025 of pure device offset (the full 4-GPU spread) — 4x the effect being chased. Action: after each pair completes, verify the `gpu` field matches the assumed alternation before trusting the running average; do not wait for all 4 to compute a verdict blind.

**2. `precond` on one seed.** Every run in this campaign uses `seed=42` (confirmed: `AUTORESEARCH_SEED` defaults to 42 in `host/dispatch.py`, and result records show `seed: 42.0`). This is a whole-campaign property, not unique to precond, so it's not fair to single out precond for extra suspicion — but it does bound what precond may claim. What CAN be claimed: three independent treat/control placements (A_s3 on gpu7, B_s2 on gpu6, B_s1 on gpu5) all show the same sign, magnitudes -0.000832, -0.000789, -0.001193 against their own per-GPU control means, all >2.9x the 0.000271 resolution — that is a real, reproducible-under-this-host effect at seed 42. What CANNOT be claimed: that it generalizes across initialization/data-order seeds, or that -0.001147 (the single best-vs-best number quoted) is the true effect size rather than one draw from a ~0.0008-0.0012 range. Report the range, not the extremum.

**3. Most likely wrong thing.** The campaign's implicit model that GPU-level counterbalancing fully absorbs host contention. `direction.py` states V3 is input-pipeline bound (~94% of charged time in the frozen CPU packing loop, per prior campaign learning echoed here), meaning the dominant nuisance is CPU/core contention shared host-wide, not per-GPU. The current device model (per-GPU control means + within-GPU sd) was built while wave widths and free-GPU sets varied across 4 physical devices; it has never been validated under the current regime of exactly 2 free GPUs with 6 heavily-loaded foreign tenants. If foreign CPU load (not GPU load) is what actually drives step-count variance, restricting to gpu6/gpu7 doesn't protect the estimate at all — the resolution figure could be stale for this specific host state. Cheapest decisive check: before trusting R2V/R2S verdicts, look at whether `steps` for the in-flight controls fall inside the previously measured 1010-1022 band for gpu6/gpu7, or have shifted — a shift falsifies the imported noise model immediately, for the cost of reading two already-running result files.

**4. Lessons at risk.** None are directly violated (no `wd_const≥0.4`, controls are yoked 1:1 not standalone so L029 doesn't apply, both hypotheses declare a non-degenerate activation diagnostic per L030's fix). The live risk is L003/L031: if gpu4 or gpu5 frees mid-run, the dispatcher could size a wider wave than the queue's fixed pairs expect, or a pair could split, stranding a treatment exactly as L031 describes for zloss. Watch for that, not for a currently-broken rule.
