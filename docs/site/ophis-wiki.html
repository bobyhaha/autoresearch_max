A ledger that decides what counts as knowledge

OPHIS is an automated-science system wrapped around a single, deliberately frozen machine-learning problem. An agent proposes ideas and interprets results — but schemas, fingerprints, gates, controls, and evidence decide what may be treated as knowledge. Every claim it holds is a typed record, cited to evidence, scoped to an exact experimental world, and superseded rather than edited.

00 — ORIENTATION

What this is

Two distinct things live in this repository, and keeping them apart is the key to reading it:

The object of study

A nanoGPT-style language model in train.py — a materially modified fork of a Karpathy-derived baseline (+707 / −45 lines across 79 hunks). Architecture, optimizer (Muon/NorMuon), schedules, and hashed n-gram value embeddings are all levers. lib.py holds tokenizer/data helpers, prepare.py builds the dataset cache, observable.py owns instrumentation.

The instrument

The vibeautoresearch package plus the research/ ledger: 21 JSONL registries, 19 typed record schemas, and a 9-command CLI that validates the graph, audits it, gates execution, and renders the current research state.

The problem it exists to solve

The system's own documentation states it plainly: the loop "tests hundreds–thousands of interventions against one metric." Under those conditions, the best result you find is almost certainly noise. The expected best-of-N |z| under pure noise grows like √(2 ln N) ≈ 3.7 at N = 1000 — meaning a 3.7σ "discovery" is exactly what you should expect from a thousand null candidates.

Nearly every rule in this repository is a defense against that single failure mode: pre-registered falsification criteria, measured noise floors, multiplicity correction, hold-out confirmation on fresh seeds, concurrent paired baselines, and an append-only history that makes retractions visible instead of silent.

The loop is not an invitation to generate arbitrary observable combinations. The agent proposes and interprets; schemas, fingerprints, gates, controls, and evidence determine what may be treated as knowledge.

The five questions

The system organizes an agent around five questions, and each maps to a stage of the loop:

  1. What do we currently know? → Knowledge
  2. What can we currently observe, control, and evaluate? → Toolkit
  3. Which falsifiable idea is most worth testing next? → Ideas
  4. How can that idea be tested reproducibly? → Experiments
  5. How should the result change current knowledge and future priorities? → Refinement

The four invariants

Stated in docs/AUTOMATED_SCIENCE_SYSTEM.md as the philosophical spine:

Facts and interpretations are different objects

"A run value is a fact. An observed pattern is exploratory. A mechanism is a causal explanation. A belief is the current interpretation of cited evidence. Changing a mechanism or belief never changes a run fact."

Stable IDs and versions

All durable entities have typed IDs. Definitions that affect scientific meaning carry versions and fingerprints. Changing a formula, tensor source, trigger, action, outcome detector, control, or experiment design creates a new version.

Tags are not specs

Tags support retrieval. They never replace a formula, context, action contract, control, outcome definition, seed list, or analysis plan.

Markdown is a view

JSONL registries are authoritative. RESEARCH_STATE.md is generated from them and must not be edited manually.

The layer separation, made concrete

Four layers, deliberately never collapsed into one another. This is the single most important structural idea in the repository:

LayerHoldsHas an assessment?May back a belief?
runsraw execution facts + measured valuesnono
observationspatterns + required possible_confoundsnono
evidencefacts + typed assessment + 4-axis trustyesyes
beliefsversioned standing conclusions, scoped— it is the interpretation—

A RunRecord's own docstring states the rule outright: "Immutable execution facts. Analysis belongs in evidence, not here." An EvidenceRecord's says: "Immutable measurements plus a clearly labelled assessment." The separation is enforced in the type system, not left to convention.

01 — ORIENTATION

The frozen challenge

Every measurement in this repository is judged against one deliberately immobilised setting, pinned by a scope key in research/setup/reconciliation.json. These four fields are the identity of the experimental world:

data_split_sha256 = ed8ea0554010df9fbfa47746adc6643d6446797753eb377c0b35413bdcf2fca3
max_steps        = 2000
stop_mode        = "steps"
outcome_id       = "out_val_bpb"

Train on shards 1–10, validate on held-out shard 6542, measure val_bpb (bits per byte, lower is better), stop at exactly 2000 optimizer steps on a single H200. The scope key is structurally validated too: data_split_sha256 must be a 64-character lowercase digest that also matches frozen_files["data_split.json"], and max_steps must be an integer ≥ 11.

Why fixed steps rather than wall-clock minutes? Because minutes can be gamed. A faster kernel, a better compiler flag, or a throughput trick buys more steps in the same time and lowers the metric without any method improvement. Fixing steps removes kernel and throughput gaming from the board entirely — the earlier 5-minute framing was retired precisely for this reason.

Three axes that must not move

From agent.md: a lower val_bpb is a real result only if it comes from a method change on a frozen playing field.

Data content frozen

The exact shard set in data_split.json. Adding, removing, swapping, or enlarging training shards — or substituting "better" data — moves the data-quality axis, not the algorithm. It invalidates the comparison outright.

Compute budget frozen

Identical MAX_STEPS across control and treatment, always. Raising steps lowers val_bpb on its own because the model is compute-limited.

Evaluation frozen

Held-out shard 6542, BPB metric, endpoint measurement — never a mid-run probe.

What you may vary: architecture, optimizer, schedule, regularization, initialization, and any model/training method change — plus data order.

The data-order subtlety

An intervention may change the order tokens are seen in (curriculum, reshuffle-between-epochs, packing) but never which tokens are trained on. And the order change must be a policy held identical across the paired seeds — never a fresh random shuffle. The reason is sharp: order is already seed-dependent, so a random reshuffle merely re-measures seed variance and tells you nothing about the policy. This matters most in this repeated-data regime (~1.6 epochs), where how repeated data is presented shapes overfitting.

The repeated-data regime

Only ~11 shards exist locally (~15M tokens each, ~151–166M unique total) and the box has no network to fetch more. At 2000 steps the training stream is 294.9M tokens — so the data repeats roughly 1.6×. This is not incidental; it is the research frontier the program targets: "map and exploit headroom in the repeated-data training regime, with emphasis on how recipe optima and mechanisms shift with training horizon."

A prior branch restricted training to shards 1–3, a much harsher ~5-epoch overfit that inflated val_bpb from ~0.95 to ~1.05. That was corrected on 2026-07-19 by restoring shards 1–10 — and every figure measured under the broken split is explicitly marked STALE — DO NOT USE.

Why the two sigmas matter — the 7.43σ story

Same-seed training is nearly deterministic, so measuring a delta against σ_repro inflates significance by roughly 3×. The documentation names a specific casualty: a write-up's claimed "7.43σ" was really ~2.6σ on the correct sigma. The rule: "The σ for a claim is seed-to-seed + temporal heterogeneity, NOT same-seed reproduction noise."

σ is also budget-dependent, not a constant: σ_repro ≈ 0.00009 at 2766 steps but ≈ 0.00062 at 1660 — a 7× difference. At fewer steps the loss curve is steeper, so identical kernel nondeterminism moves the metric more. Both quantities must be re-measured whenever the budget or data config changes.

What "beating RSI" actually means

The external RSI number (0.9109) came from a richer sandbox: B200 hardware, flash-attention that honours sliding windows, and the full no-repeat 400B corpus. This repository runs H200 + full-causal SDPA + ~10 repeating local shards. Absolute numbers are not comparable across sandboxes. RSI 0.9109 is a threshold to beat, not an internal control. The valid target is beating our own same-data, same-compute local baseline of 0.930647 with a genuine method change that clears the paired-seed gate.

The Toolkit feeds Ideas from the side: it defines what can be observed, changed, held fixed, and scored. A hypothesis may only reference tools that already exist as registered, executable records — "Do not approve an experiment that pretends the tool exists."

The whole ledger — explore all 21 registries

21 registries declared in manifest.json (schema version 1.2), of which 9 are declared append-only. Counts are live working-tree record counts. Click any registry to see its purpose, enforced invariants, complete field list, and a real record from the ledger.

Every file's first line is a # comment header, so raw wc -l overcounts each registry by exactly one. Example records are real, with long string values truncated for display.

Finding: append-only is a convention, not an API guard

The append_only flag is passed to nine registries and stored at registry.py:35 — but it is never read anywhere in the codebase. It does not gate add(), load(), deletion, or in-place editing. The manifest's append_only array is likewise not validated by _manifest().

Append-only is upheld instead by three other mechanisms: add() only ever opens the file in "a" mode; content fingerprints detect any edit to an existing record; and supersession chains are validated (including cycle rejection). So a hand-edit is caught, but not blocked.

The completeness gate

The registries are the deliverable, not a side effect — but filled proportionately: each experiment populates the records it depends on and produces, not every registry on every run. Two commands enforce this per experiment:

  • check-gate (pre-run) refuses to freeze an experiment whose motivating observable is not registered-and-executable, or whose mechanism cites literature claims lacking an evidence assessment.
  • audit (post-run) flags a completed run with no evidence, a hypothesis with no evidence, or a belief with no evidence.

The required cycle is mechanism → hypothesis → gated experiment → run → evidence → belief → decision — including nulls and contradictions. A cycle leaving any of these empty is unfinished.

03 — THE LEDGER

Knowledge

Six registries that separate what a paper said from what we measured from what we now believe.

Papers — citation metadata only

A paper record contains no scientific assertions. It holds title, authors, year, venue (with an explicit peer_reviewed boolean), a primary URL, a retrieval date, and a status of active / superseded / retracted. All 349 are currently active.

pap_muonfingerprint 4facb73fbc4b0daa

"Muon: An optimizer for hidden layers in neural networks" · Keller Jordan · 2024 · venue blog, peer_reviewed: false · status active · notes: "Seeded literature prior for the training-methods knowledge base."

Why peer_reviewed is a first-class field: it feeds the downstream trust evaluation without laundering an unvetted source into settled fact. Muon originated as a blog post, and the record says so. That lets a later assessment rate it strong on directness (the author invented the method) while capping design — a nuance a single "credibility" score could not express.

The status field is currently inert. It appears nowhere in the codebase except its own enum validation, and all 349 papers share the same value, so it carries zero information today. Its purpose is forward-looking: if a paper is retracted, you flip the status rather than delete the record — because claims and evidence already point at that paper_id, and deleting would orphan them.

Claims — atomic, typed, and deliberately statusless

A claim is one atomic statement extracted from a paper, typed into one of eight categories, with its own scope, limitations, and a locator naming where in the paper it came from (e.g. "method definition" vs. an abstract boast).

Claim typenClaim typen
method_definition242predictive110
descriptive238negative_result52

mechanistic127temporal_association11

A claim has no status or assessment field. Its "assessed" state is derived entirely from whether an evidence record cites its claim_id. This is deliberate: the claim is provenance, a frozen record of what a paper asserted, and it is never edited to match a run.

clm_muon_1type: mechanistic · locator: method definition

statement: "Orthogonalizing each 2D parameter's momentum update via a Newton–Schulz iteration equalizes update magnitude across singular directions, so hidden matrices train faster per step than under Adam."

scope: applies_to: 2d_hidden_matrices · domain: transformer_lm_pretraining

limitations: "Effect strongest for well-conditioned hidden layers; not shown for embeddings."

Because this claim is typed mechanistic, the ingestion protocol requires it to record direction of effect and the scope in which it holds — hence the explicit "trains faster" direction and the 2d_hidden_matrices restriction. That scope is why real Muon setups are hybrid: Muon governs 2D hidden weights, Adam handles embeddings and scalars. Two OPHIS beliefs (blf_cautupd_hurts, blf_adam_warmdown_optimal) turn on exactly that split.

The 1012 vs 16 gap

Only 16 of 1012 claims have a literature-evidence assessment — 996 unassessed. (Run evidence cites 7 unique claims, all a subset of those 16, so the union is still 16.)

This is by design, not neglect. Claims are harvested broadly and cheaply — 349 papers seeded in a day. An assessment is an expensive judgment about transfer to this exact setup, written only when a hypothesis is about to consume an experiment slot. The protocol is explicit: "Do not start an experiment merely because a paper is interesting." The 996 is a visible backlog of unmined priors, not a bug.

Evidence — measurements kept apart from judgment

One EvidenceRecord type serves both literature and runs, with mirrored requirements enforced in __post_init__: literature evidence requires paper and claim ids; run/offline evidence requires run ids. Each record carries three separated blocks:

facts — the measurements

Immutable. Verbatim per-seed deltas, or what the papers actually reported. No interpretation. Must be non-empty.

assessment — the judgment

relation ∈ supports / opposes / mixed / inconclusive / not_tested · strength ∈ none / weak / moderate / strong · plus limitations.

trust — source quality

Four axes — design, replication, scope_match, directness — each ∈ weak / adequate / strong / not_applicable, with reasons in limitations.

Why four trust axes instead of one score? Because they move independently and the difference is actionable. A blog post by a method's inventor can be strong on directness while only adequate on design and replication. A rigorously-replicated paper run at 100× the scale is strong on design but only adequate on scope_match. Collapsing these into one number destroys exactly the information that determines whether a prior transfers.

Literature evidence is unanimously optimistic; reality says no 58% of the time. That is the system working as designed: you only bother assessing literature for directions you already believe in, so the prior is biased by construction — and the runs are where that bias gets corrected. Every failure is recorded as first-class evidence because the protocol requires recording "null, failed, and contradictory results."

Strength distribution across the 50: 25 strong, 16 moderate, 6 weak, 3 none. Scope-match tells the story from the other side — 49 of 50 are scope_match: strong, because the evidence is the frozen challenge. Literature evidence sits at adequate; that one downgrade is why literature assessments cap out at moderate strength.

The single non-strong record is instructive: evd_run_ngram_256x_transfer_2766_diagnostic has scope_match: not_applicable. It is a beautiful statistical result — 3 paired seeds, mean −0.004276, t = −17.3 — but it ran at 2766 steps, not 2000, so it is labelled "OFF-BUDGET DIAGNOSTIC … NOT an adopt input." A t = −17.3 result at the wrong budget is marked not-applicable rather than strong. That is scope_match doing precisely its job.

The crossover records

16 of the run-evidence records carry both run_ids and claim_ids. That is the claim-revision mechanism: when your runs contradict a paper, you do not touch the paper or the claim — you file run evidence that cites the claim with relation opposes or mixed. The literature record stays intact as provenance; the disagreement is a new, dated, fingerprinted layer on top.

Observations — patterns that are not yet evidence

An observation records something noticed in run data that you were not testing for. It has no trust, no assessment, no method — instead it is required to carry possible_confounds, forcing you to state how you might be fooled. run_ids must be non-empty. It can never back a belief.

Observation IDs live in the evidence namespace (evd_obs_*) for a documented reason — the code comment reads: "Observations use the evidence namespace because they may later be promoted."

StatusnMeaning

Real examples show the type earning its keep:

  • evd_obs_ngram_capacity_vram_linear — VRAM scales ~linearly with table size (64×≈14GB, 128×≈57GB, 256×≈113GB), implying 512×≈226GB would OOM a 143GB H200. This is what bounded the capacity sweep at 256×. Confound noted: "allocator caching; early readings understate steady-state."
  • evd_obs_pipeline_not_bitwise_deterministic — three 30-step runs at fixed seed and code do not reproduce bitwise.
  • evd_obs_sota_snapshots_were_not_runnable — all four SOTA snapshots failed on import.

Three observations are flagged followup_required: true and remain unresolved, including evd_bug_fourgram_gate_uninitialized — the bug that retracted ten runs.

Terminal ≠ current — the demotion mechanism

Being the newest version does not make a belief authoritative. render-state re-checks each belief's scope key against the live setup key and demotes any mismatch to [unscoped]. Running the real render logic against the live registries today gives: 63 records → 20 superseded → 43 terminal → 36 in-scope → 35 verified, 1 provisional, 7 stale.

When the challenge reset from the old 3-shard regime to the frozen 2000-step one, the entire prior config-tuning ledger demoted at once — that is the intended behaviour, not a failure. The populated-ledger policy states it directly: historical terminal beliefs "do not become current merely because they were never superseded."

Does a belief use external knowledge? In two different senses. 21 of 63 name a paper claim in subject_ids — they adjudicate the literature. But zero cite a literature-evidence record as backing; all 49 evidence-backed beliefs rest on internal runs. The engine explicitly permits literature-only beliefs (they bypass the ≥3-seed requirement at registry.py:816) — nobody has used that path. External knowledge sets the agenda; internal runs settle it.

Observables — the instruments

An observable defines a measurement of internal dynamics: sources (each with name, target, tensor_type, declared axes, context), an operation, reductions, an output (type + units), a collection block (mode, cadence, cost tier, estimated overhead, profile status), and a causal_availability block.

Enforced: reductions must be total

For an axis_reduction_pipeline, the sorted reduction axes must exactly equal the sorted declared source axes — "axis_reduction_pipeline must reduce every declared source axis exactly once." You cannot declare a source with axes [layer, head], reduce only layer, and call the result a scalar. Ill-defined measurements are unconstructable.

The causal_availability block (available_before_action, uses_validation, stage) is what lets the system reason about whether a signal may legitimately drive an intervention. An observable that touches validation is diagnostic-only, structurally.

Contexts — why exactly one

A context describes the conditioning state present before any action — the schema's required field is literally availability.available_before_action.

ctx_five_minute_h200stale naming

value: {accelerator: "NVIDIA H200", seed: 42, time_budget_seconds: 300} · entrypoint lib.py:TIME_BUDGET, train.py:_SEED

There is exactly one context because the entire methodology holds the environment constant and varies interventions. More contexts would only appear if you deliberately compared across environments — which the fixed-compute rule forbids for adoption decisions.

Note the drift: this record encodes time_budget_seconds: 300 — the retired 5-minute regime, not the current 2000-step one. It is not load-bearing (the real scope lives in setup reconciliation, and the protocol says static comparisons should omit contexts entirely) but it is stale.

The single outcome

out_val_bpbEndpoint validation bits per byte · version 1 · unit_tested

metric val_bpb / bits_per_byte · direction minimize · data_split validation · aggregation endpoint (evaluate_bpb) · detector.finite_required true · policy_visible false

Entrypoint train.py:evaluate_bpb final eval, test test_validation_bpb_is_endpoint_metric.

direction: minimize is why every improvement in this repository appears as a negative delta. finite_required means a NaN/inf run is rejected rather than scored.

Enforced: the leakage firewall

If data_split is validation or test and policy_visible is true, construction raises "validation/test outcomes cannot control online training." The contaminating configuration is not discouraged — it is unconstructable. A signal that steers training must live in a separate record on the train split. Without this, the training loop could optimise toward the validation set directly and every result in the ledger would be worthless.

Tool proposals & capability gaps

A matched pair: a tool proposal says "here's a tool we should build"; a capability gap says "here's the scientific question we can't answer without it." Both exist so a blocked idea is recorded honestly rather than silently dropped or faked — "Do not pretend a tool exists, and do not silently skip the measurement."

Two proposals, both proposed: tlp_smoothed_train_val_gap (observable, light) and tlp_reference_model_slm (intervention, heavy).

Ideas

Where knowledge becomes testable. Mechanisms say why something should work; hypotheses say what exact result would prove it wrong.

Mechanisms (17)

A mechanism is a falsifiable causal story, not a hunch. Required: a causal_chain of at least two steps (enforced), assumptions, competing_mechanism_ids, scope, and predicted observable/intervention behaviour.

mech_ngram_short_context_memoryorigin_type: literature · status: active

causal chain: "Local bigram/trigram context carries next-token information a token-only embedding misses." → "Hashed n-gram embedding tables cache this signal and, gated into the attention value path, make it available cheaply." → lower loss.

assumptions: hash collisions are tolerable at the chosen table size; the learned gate can down-weight noisy n-gram rows; the benefit persists in the 2000-step repeated-data regime.

claim_ids: 7 claims across modded-nanoGPT, N-Grammer, SCONE, infini-gram.

Enforced: provenance must be honest

A literature mechanism requires claim_ids. A self_proposed mechanism is forbidden from citing claims — "self-proposed mechanism cannot claim literature provenance." Its empirical grounding is meant to come from observation_ids instead. That is the designed promotion sink for observations.

Split: 13 self-proposed, 4 literature; 9 active, 8 proposed. But zero of the 17 cite any observation. So all 13 self-proposed mechanisms currently have empty provenance — barred from citing papers, and not citing observations either. The graph edge exists and is validated; it has simply never been filled in.

Hypotheses (39)

A hypothesis converts a mechanism into one pre-registered bet, linking exact observable, trigger, intervention, outcome, controls, timing, failure condition, and estimated cost. Enforced invariants include: mechanism_ids must be non-empty; observable IDs must be unique; a hypothesis requires a no_intervention control; and a trigger must reference a predicted observable unless its type is run_start or static_schedule.

hyp_ngram_capacity_2564× n-gram embedding capacity lowers 2000-step val_bpb

mechanism: mech_ngram_short_context_memory

prediction: raising bigram+trigram VE hash buckets 4× (vocab×64 → vocab×256) lowers endpoint val_bpb versus the byte-identical mult=64 baseline by more than the floor.

expected_effect: {direction: decrease, estimand: endpoint_val_bpb_delta_vs_baseline, latency_steps: 0}

falsification: "Adopt only if paired ≥3-seed mean delta ≤ −0.001694, all-same-sign, paired-t significant (confirmed on held-out seeds)."

estimated_cost: 2 concurrent 2000-step H200 runs for the pilot; discovery adds ≥3 paired seeds; tier light.

The decisive design point: the decision rule is written when the hypothesis is proposed, not after seeing results. That is the pre-registration that defeats winner's curse — you cannot move the goalposts because the goalposts are fingerprinted into the record, and a run's spec_fingerprints would detect the drift.

All 39 hypotheses carry status proposed, and all 39 name a mechanism. The status does not advance even for hypotheses that clearly ran to completion — resolution is recorded downstream in evidence and beliefs (which point back via subject_ids) rather than by mutating the idea record. "39 proposed" does not mean "39 untested." This is consistent with the append-only philosophy: ideas are the stable subject, conclusions accrete around them.

The engine & CLI

A dependency-free Python package. core.py holds primitives ("Dependency-free validation and serialization primitives"), registry.py the persistence and validation graph ("The authoritative research graph described by research/manifest.json"), setup.py the scope key ("Validate the portable identity of an experimental world"), and cli.py the interface.

Fingerprints — a seal, not storage

def canonical_json(value):
  return json.dumps(value, allow_nan=False, sort_keys=True, separators=(",",":"))

def fingerprint(value):
  return hashlib.sha256(canonical_json(value).encode("utf-8")).hexdigest()[:16]

Canonicalization guarantees the same content always yields the same bytes regardless of field order; SHA-256 then reduces it to a 16-hex-character seal.

This is one-way. A fingerprint is not a location and stores nothing — you cannot recover a record from 4facb73fbc4b0daa. It exists for two jobs: check_fingerprint recomputes the hash and raises if a declared value no longer matches (so a frozen record cannot be silently mutated — a change must become a new record with a new fingerprint), and runs store spec_fingerprints so they can prove which exact version of a hypothesis, experiment, and outcome they were executed against. Mismatch raises "hypothesis fingerprint drift."

Typed IDs are validated against 18 prefix patterns: pap_ clm_ evd_ blf_ obs_ int_ ctx_ out_ tlp_ gap_ mech_ hyp_ exp_ run_ upd_ aud_ dec_ dep_.

How execution is gated

Nothing may run unless three things hold simultaneously: the setup record status is passed; every frozen file's SHA-256 still matches (recomputed live, including the reference-code path); and the target experiment freezes the current scope key. The relevant error is blunt: "setup reconciliation is {status!r}; experiments are stopped."

A setup record can only reach passed if its baseline observed value sits within tolerance_sigma × effective_sigma of expected, using at least three unique seeds. The reconciliation is thus itself an experiment that must pass a gate.

How a belief becomes "verified"

render-state decides verified vs. provisional in code: a belief must cite evidence, and then either be backed only by literature, or draw on ≥3 distinct seeds from completed runs (registry.py:816). The ≥3-seed rule is an executable check, not a guideline — and it is why a one-seed pilot can never mint a belief no matter how good its number looks.

Gate discipline

Fixed compute per comparison

The most emphatic rule in the repository: every adopt/discard comparison holds control and treatment at identical MAX_STEPS. Cross-budget comparison is forbidden because more compute lowers val_bpb by itself — the historical curve 1660 → 0.9473, 2500 → 0.9189, 2766 → 0.9126 shows exactly how a "win" could be manufactured from compute alone.

Runs that deliberately vary compute are diagnostics only — mapping the bpb-vs-tokens curve or locating the matched-compute operating point — and must be recorded as such, never used to promote or kill a change.

A subtler trap: same steps is not same compute. A wider MLP or bigger batch does more FLOPs per step, so it can win a step-matched race by spending more. Where compute differs materially, the result must be reported as a quality–compute tradeoff, not a win. Every arm therefore records steps, tokens, wall time, estimated FLOPs, peak memory, parameter count, and batch tokens.

The verdict gate

Three conditions, all required:

  1. A paired t-test over ≥3 seed deltas (self-calibrating)
  2. All deltas the same sign
  3. |mean| above the effect-heterogeneity floor

Baselines must be freshly reproduced concurrently — same batch, GPU, and time window — because cross-time baselines carry temporal drift of about 0.0007 that a same-seed sigma cannot see. One-seed runs are plumbing pilots only; two-pair tests stay exploratory.

Selection discipline

With hundreds to thousands of interventions tested against one metric, the best-of-N is inflated by construction. A 1σ one-sided gate passes ~16% of null candidates; expected best-of-N |z| under pure noise grows like √(2 ln N) ≈ 3.7 at N = 1000. Five standing rules follow:

  1. Always report N. "376 improved ≥3σ" is uninterpretable without the denominator.
  2. Correct for multiplicity — a Bonferroni/FDR-adjusted z, or better, judge only by hold-out confirmation.
  3. Variance-aware selection. Select on the lower confidence bound of the paired delta, never the mean alone. Same-seed repetitions cannot even see the relevant (seed) variance.
  4. Hold-out confirmation. A selected candidate's selection-time mean is not reportable; re-run the top-k on fresh pre-registered seeds it was not selected on, against a concurrent fresh baseline, and quote only those.
  5. Round to the noise floor. Seven significant figures against σ≈0.0008 is false precision that hides which sigma was used.

Plus a structural defense: a never-touched test split, scored exactly once per confirmed winner, because thousands of adaptive selections against one validation shard is gradual val-set overfitting.

The exploration budget

Refinement (nudging a bracketed knob) and exploration (a structurally novel change) draw from one budget on a firm 6:4 split — 60% explore, 40% refine — counted by experiment slots, not compute, because exploration costs more per experiment and compute-budgeting would starve it.

Trailing-window rule

Over any 10 launched experiments, ≥6 must be track:explore. If it falls below, the next slots must be exploration until restored.

Anti-streak cap

No more than 2 consecutive refine experiments. A raw percentage can be satisfied by front- or back-loading; the streak cap is what actually prevents drift into a tuning lane.

Plateau rule

After K = 3 refinement pilots fail to beat the record, raise exploration to ~50% until a new validated win lands.

Reset rule

Once an exploration change is validated and adopted, return to 6:4 and refine locally around the new baseline.

The share may flex within a 50–70% explore band under those triggers, but absent an explicit trigger it holds at 6:4. The documented failure mode this guards against is explicit: a 2026-07-19 session that collapsed into a six-experiment tuning streak. Exploration vs. refinement is a distinction of structure and magnitude, not subsystem — swapping the optimizer or a data-order policy is exploration; nudging a bracketed β is refinement.

Correcting a paper

When a run contradicts published work, the claim record is never edited — it is provenance. Instead: (1) keep the claim unchanged, (2) file run evidence citing the run IDs and the claim ID with relation opposes or mixed, (3) append a belief with status challenged / contradicted / context_dependent superseding the prior, and (4) state the scope in which the paper's result fails to reproduce here versus the scope the paper reported.

Literature priors are corrected by local evidence through beliefs, never by rewriting the claim.

Why the ladder stops

Going 4→5-gram, the fraction of positions whose context never recurs jumps from 45.8% to 69.9%, and the median context is seen exactly once. "A hashed VE row for a singleton context receives one gradient in the entire run and cannot generalize — the 5-gram rung is starved by construction at this token budget."

The order ceiling is therefore a data-budget artifact, not an architectural limit — and the first thing to retest if the step/token budget is ever unfrozen. The measurement also independently reconfirmed the single-pass regime: the stream is exhausted inside shard 5.

Note the care in the negative claim: the 5-gram point estimate is still negative (helping), merely too small to clear the gate. The honest conclusion is "not worth its cost at 2000 steps," not "5th-order context is useless." Similarly, a gappy-4 probe showed the 4-gram win does not depend on contiguity — what the rung buys is the existence of a 4-token conjunction, not its adjacency structure.

A naive reading that was wrong

The apparent "1.66× bigger improvement on rare tokens" from the capacity win is an artifact. A causal observable probe (val nats by frequency decile, 64× vs 256×) showed relative improvement is flat-to-declining with rarity — 5.26% frequent vs 4.14% rare — and flat across position. Rare tokens simply have more loss to give. This substantially weakened the "collision interference on rare n-grams" rationale for brute-force capacity scaling.

12 — FINDINGS

Integrity findings

The campaign summary devotes a section to seven mistakes that each changed a conclusion or a claim. It is the most unusual thing in this repository, and the most valuable.

Finding 1 — the false negative that became SOTA

fourgram_gate was created and used in the forward pass but omitted from init_weights. Because the model builds on meta then calls to_empty(), it held uninitialized GPU memory for every run with NGRAM_FOURGRAM_MULT>0 — the 4-gram signal was being injected through a random gate.

10 runs retracted and the conclusion "n-gram order is redundant with capacity" withdrawn. After a guarded zeros_ init, the axis was re-measured and won (−0.001307, 6/6 hold-out seeds, t = −26.27), becoming SOTA #4. It had been a false negative all along. The re-measurement also required the row-wise-state and sparse-gradient infrastructure, since the configuration previously OOM'd at ~151 GB and now runs at 76.6 GB.

Finding 2 — incompatible units

DIAGNOSE reports mean nats per token; val_bpb is per byte. Its mask is a byte indicator, not a count, so the two can move in opposite directions — demonstrated on the seg contrast, where val_bpb improved by −0.00173 while per-token nats worsened by +0.0801 in all eight position bins. Since the val set is identical, implied bytes/token would have to differ by 3.3%, which is impossible. Consequence: the seg-mask position causal test is not runnable with that instrumentation, and any DIAGNOSE contrast whose two metrics disagree in sign must be discarded.

Finding 3 — reserved key

The product-key memory used nn.ModuleDict key "values", colliding with the reserved dict method and raising KeyError at construction. Caught by a smoke test before any experiment ran — the one finding that cost nothing.

Finding 4 — an overclaim retracted

The pipeline is not bitwise deterministic. Three 30-step runs at fixed seed and code: v10 run1 5.068482, v10 run2 (same binary) 5.066724, v11 5.070265. v10 disagreed with itself by 0.001758 — matching the 0.001783 v10↔v11 gap it was being compared against, so the new lever was indistinguishable from run-to-run nondeterminism.

Every "byte-identical when off" claim was therefore downgraded to structural identity ("no added ops or memory when off"), verified via capture-site counts and peak VRAM rather than equal loss. Notably, this was checked because the lever looked provably inert by inspection — the same reasoning that produced the finding-1 false negative.

Finding 5 — the ritual that was never tested

All four SOTA snapshots were not runnable: each omitted observable.py, which train.py imports unconditionally, so each failed instantly with ModuleNotFoundError.

"Hash verification could never have caught this: all four recorded hashes verified correctly, because hashes validate the files that are present and say nothing about a file never included." The reproducibility ritual had been performed four times and never once tested. After the fix, sota_004 reproduced end-to-end at 0.923582 vs a recorded 0.923642 (Δ = 0.19 σ_repro), with peak VRAM matching exactly.

Finding 6 — the vacuous check

A verification step read o.get('errors') while the validator emits error (singular), so it returned None regardless of state. Several "validate clean" confirmations were meaningless — including one written into a commit message — while two records were citing an ObservationRecord in evidence_ids, where only evidence records are permitted.

Finding 7 — a label, not a configuration

The configured TTTL attention windows are not executed by the frozen SDPA path: attention_func ignores window_size and runs full causal SDPA; the window applies only for DOC_MASK_MODE=window|both, not the winning seg mode. Paired comparisons remain unbiased (both arms share full-length attention), but "TTTL baseline" was only a configuration label, and the old FLOP telemetry undercounted attention.

The pattern

Findings 1, 5, and 6 share one root cause, named explicitly: verification that inspects rather than executes.

An uninitialized gate that looked initialized, a snapshot that looked complete, a validator call that looked clean. Each was caught only by running the thing.

14 — FINDINGS

A belief reopened — the ledger self-correcting

The clearest demonstration that supersession is a live mechanism rather than a design document. It happened while this reference was being compiled.

A belief, blf_env_lever_space_exhausted, had concluded that the accessible environment-lever space on the frozen challenge was exhausted — 33 experiments across 8 axes, with WARMUP_RATIO=0.02 testing null as the final lever. That is a strong, load-bearing conclusion: it is the claim that justifies abandoning knob-search entirely and moving to structural work.

Then the warmup experiment was re-examined. The retraction evidence records what was found:

evd_run_ngram256_seg_warmup002_retractednot_tested · strength none

consequence: "The WARMUP_RATIO=0.02 arms and the 256x+seg control arms trained the IDENTICAL schedule. The three paired arms differed only in a logged configuration string, so the reported deltas (−0.000006 / −0.000036 / −0.000154) …"

The knob was dead. Setting it changed a logged string and nothing else. The three "paired arms" were the same configuration run twice, so the deltas measured pure run-to-run noise — which is exactly why they were so implausibly tiny. A null result had been read as "this lever does nothing," when the truth was "this lever was never applied."

The system's response is precisely what the protocol prescribes, and none of it involves deleting anything:

This is the challenged status — one of the three reserved for contradiction — in genuine use, and it is why the belief count moved from 62 to 63 and the status table gained an entry. The v1 record remains in append-only history, readable, with its reasoning intact. Anyone reading the ledger later can see not just that the conclusion changed, but why, and which specific piece of evidence broke it.

The generalizable lesson

This is the same failure mode as integrity findings 1, 5, and 6: a check that inspected rather than executed. A configuration string was logged, so the lever looked set. Nobody verified that the resolved schedule actually differed between arms. The tell was there in the data — deltas of −0.000006 are far below even same-seed reproduction noise, which should read as "nothing happened" rather than "no effect."

A null result and a dead knob produce identical-looking output. Distinguishing them requires checking that the treatment was actually applied — which is why promotion_gate criteria for the capacity pilot included the line "RESOLVED_CONFIG shows NGRAM_TABLE_MULT=256 on treat / 64 on baseline." That check exists because this class of error was anticipated; here it simply was not applied.

The recurring shape

Most seams are the same species: a discipline enforced at the point of creation, but not maintained afterwards. Statuses that never advance, ladders never climbed, cleanup passes never run, generated views never regenerated.

The invariants that are enforced — leakage, provenance, scope, budget caps, fingerprints — hold perfectly, because they raise a SchemaError at construction and nothing can proceed. The ones that depend on someone coming back later are exactly the ones that drifted. That is a general lesson about where to spend enforcement effort, and this repository is an unusually clean natural experiment in it.
