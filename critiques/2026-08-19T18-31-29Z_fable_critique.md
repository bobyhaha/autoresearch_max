**Q1 — is `_IMPLEMENTED` the reason?** No. The guard in `build()` computes `{m for m in _d.MECHANISMS if cfg.get(m) is not None} - _IMPLEMENTED` — it inspects only the six names in `direction.MECHANISMS` ("mtp","unet","zloss","noqknorm","prefetch","precond"). It correctly kills `prefetch`. But the ten offending keys are in NEITHER `direction.MECHANISMS` NOR `direction.KNOB_AXES`: they are unknown to the entire policy, no knob branch reads them, so `build()` applies only the universal instrumentation and returns what is effectively the control. `direction.unknown_keys()` exists for exactly this ("Config keys no policy rule covers. Never silently ignored") — but `build()` never calls it. The one-line systemic fix: at the top of `build()`, `bad = _d.unknown_keys(cfg); if bad: raise VariantEditError(...)`. Making the ten real requires NEW knobs/branches in every case — none is a bug in an existing knob (contrast the historical `mu_const` case, where the branch existed but its `sub()` target was wrong). Nuance: several are one-line knobs against existing baseline constants — `warmdown` targets `WARMDOWN_RATIO = 0.5` (baseline/train.py:453), `lmhead_beta1`/`adam_b1_hv` target the `betas=adam_betas` literals in `setup_optimizer` (lines 258–259) — while `periln`, `namo`, `kroninput`, `muonscope` need genuine mechanism branches.

**Q2 — L053 vs the fused z-loss.** Confirmed: L053 (`lit/lessons.jsonl` line 57) carries `blocks_keys: ["zloss"]`, and `claims.blocking_keys()` refuses ANY cfg containing the key — while its own `applies_when` says an implementation "that REUSES the logsumexp cross-entropy already computes internally" is "NOT covered, and explicitly left open". So the lesson mechanically forbids the experiment it declares open. Narrowing to `blocks_values` CANNOT fix this: `blocked_values()` predicates on the key's numeric value (`op`/`value`), and L053's own diagnosis says "the z-loss cost is INDEPENDENT OF LAMBDA" — the blocked dimension is the implementation (a second vocab-width pass; the generated arm literally runs `for _i in range(0, _flat.size(0), _CH): _acc = _acc + (torch.logsumexp(_flat[_i:_i+_CH], dim=-1) ** 2).sum()` as a separate pass), not any coefficient range. **Cleanest fix: a separate knob**, `zloss_fused`, with its own `build()` branch that replaces `F.cross_entropy` with an explicit logsumexp-based CE (`_lse = torch.logsumexp(flat, dim=-1); loss = (_lse.gather-free NLL); loss += W * (_lse ** 2).mean()`) so log Z is a free byproduct of the one existing pass. L053's `blocks_keys: ["zloss"]` then covers exactly the separate-pass arm it measured, and L054's prescribed follow-up (fused at 1e-4 plus a weight-0 fused arm to price the manual CE) becomes registrable without weakening the lesson. Add `zloss_fused` to `direction.MECHANISMS` and `_IMPLEMENTED` together.
